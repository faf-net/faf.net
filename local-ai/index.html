01

What runs here

The NAS with the card in the dock runs what you would otherwise take from a cloud service: chat, agent, pictures and coding, also reachable through a messenger and from your own programs. The computing happens at home.

Chat in the browser

Open WebUI

Like a chat service from the cloud, except that the answers come from your own card: one account per person, history, file upload, web search through an own SearXNG.

first word after a break: 21 s · then about 70 tokens/s
Agent

Hermes Agent

An agent you reach in the browser or through a messenger, that uses its own tools and runs tasks on a schedule, with up to 256K tokens of context. Rules in the system prompt and a small checker keep it from making things up.

made-up things recognised with the rule: 104 of 120
Messenger

Signal

Write to the agent from your phone like to a contact, also when away from home. I recommend and prefer Signal, because messages there are end-to-end encrypted. I have also tested Telegram and Discord successfully.

runs through the agent · end-to-end encrypted only with Signal
Pictures

ComfyUI

"Make a picture of …" in the chat or the messenger: the switch unloads the language model and loads a picture model onto the same card. Both at once do not fit into 24 GB.

8–66 s per picture · swapping from the language model 21–27 s
Coding in the terminal

OpenCode 2

A coding agent in the terminal that reads and changes files and runs commands. It talks to the same address as the chat, and you pick the model in the session. The code stays at home.

shares the card with chat and agent: one request at a time
Your own programs

API in the OpenAI format

Any program that can talk to a cloud service in the OpenAI format can be pointed at the address in the home network instead: scripts, editor extensions, automations. No account with a provider is needed.

about 70 tokens/s · one address, the call picks the model

Three things leave the house: the search queries of the web search, the addresses of the pages the agent reads, and the messages that travel to the agent through the messenger service (end-to-end encrypted with Signal; with Telegram and Discord the service can read along). The search queries go out through a VPN: the search engines see the VPN provider's address, not your own line. The pages are fetched by a web reader, Crawl4AI on the iDX, through a VPN as well; the target sites, too, see the VPN provider's address, not your own line. Everything else, including every uploaded document, stays on your own machines.

02

The NAS stays a NAS

Even with the model loaded, everything the iDX was bought for keeps running: photos, video and file shares. The card in the dock takes nothing away from them, because they have a graphics unit of their own.

The iDX keeps doing what it was bought for, with the services UGOS brings along: Photos for the photo library, Video for the media library, file shares over SMB and UPS monitoring. Docker comes from UGOS too; chat, search and agent run in it. The built-in Arc iGPU stays free for transcoding and photo recognition, the card in the dock only runs language and picture models.

While the model was writing, a 17.7 GB file came off the NAS at 1,174 MB/s (1,175 MB/s without a model; the receiver sat on the same network with 10 Gbit/s, which the transfer nearly filled). Transcoding 4K to 1080p on the Arc iGPU dropped from 290 to 156–245 frames per second, still 5 times as fast as playback. The model's decode speed did not change (measured on 19 Nov 2026 on my own build; with the uncensored version one of the two requests affected was 5 % slower). Not measured: SMB.

The price is memory: with the 125B model loaded, 4.2 to 7.4 GiB of the 62 GiB stay available, depending on the version (measured on 19 Nov 2026). A second large service does not fit next to it.

Is the card in the dock worth it?

UGREEN ships the iDX with an AI console that loads its own model onto the built-in Arc iGPU. The same file, three paths:

On the card the built-in model writes 11 times faster than as shipped and needs 0.7 instead of 2.1 Wh per 1,000 tokens. The CPU alone out-writes the iGPU server but reads a prompt about seven times more slowly. "As shipped" is the server UGOS starts by itself after the download; I measured it through its Unix socket. The AI console's second runtime is a CUDA build and does not start with an AMD card.

And the quality? The same tasks for both models

The small model writes almost twice as fast but thinks much longer: 2.7 times as many tokens for the same tasks, and in nine tasks the reasoning budget was used up before an answer came. In return it leaves the RAM of the NAS free. If you mainly want a NAS and chat now and then, the small model on the card serves you well; for an agent and long texts the big one pays off.

04

A 125B model on 24 GB

Qwen3.8-Flash-Next is a Mixture-of-Experts model: only a few experts run per token. Strata keeps the frequently used ones in VRAM and the rest in the iDX's fast RAM. It runs in three versions: uncensored in daily use, the original for the first measurement and as the fallback, and a smaller quantization only for comparison.

Decode speed stays at 54 to 59 tokens per second between 1K and 248K tokens of context. From 16K on my own build reads 2,300 to 3,000 tokens per second, the unchanged release about 1,300, over a PCIe link with only four lanes. What the own build is and how it was checked is in chapter 5.

Decode speed depends on the text, which is why this page shows different numbers: the draft head (MTP) proposes several tokens at once and is right more often on predictable text. Long answers come at 68 tokens per second with the original and at 67 with the uncensored version in daily use; Strata's own benchmark gives 82 in its agent part and 72 in its chat part, and a little less after a very long prompt. The round 70 in the page header sums up the values for long and for short answers.

For comparison, a dense 70B model (Llama 3.3, Q4) on the same card: 2.7 tokens per second, because every token reads all weights and half of them sit behind the CPU.

Six models on the same card

Smaller models that fit entirely into video memory run on the card as well. Two dense models write at half the speed of the 125B model and do not pass more tasks. UGREEN's bundled Qwen 3.5 writes fastest but has the weakest German and passes the fewest tasks. Only the versions of the 125B model are both fast and good at German; the uncensored one leads in German. The numbers in this chart are from Strata 0.2.12; on 0.2.14 the 125B model passes 98 instead of 96 of 102 tasks. One or two tasks flip between two runs of the same release, so 96 and 98 mean equal.

And against a model in the cloud?

Waiting times in everyday use

In a running conversation the answer comes at once, because the model keeps the conversation so far. It reads a long text once; follow-up questions on it are fast again. After 30 minutes without a request the model is unloaded and loaded again next time. For shared use, pick one model for everyone: if two people alternate between two models, the card reloads every time (20 s).

What it does differently

Strata's engine ships switches for prompt reading that are off on this card generation because several of them change the rounding. My build carries a table of 27 of them in the code and turns them on when exactly one discrete RX 7900 XTX or XT is visible under Linux; the engine newly sets 26 of them, one is already on in the release. No prompt-reading switch is left in the run config. Whatever you set yourself is never overwritten, and STRATA_GFX1100_DEFAULTS=0 turns everything off. The change is about 200 lines in five files and lives, with build instructions, in a repository of its own: faf-net/strata-xtx. It is an unofficial fork, not a Strata release.

Steel blue is the unchanged release, amber my own build, both on Strata 0.2.16, measured alternately on 19 Nov 2026 with Strata's own benchmark, card in my quiet setting. Over the whole depth the original reads 2,404 tokens per second at 16K, 3,021 at 65K and 2,907 at 248K; the variant with control vector that my agent works with reads 2,290, 2,925 and 2,890. 250,000 tokens are read in just under a minute and a half; the release takes well over three. Decode stays the same.

Checked before it went into use

Every version goes through the same chain, with both models. Quality: my task set gives 97 of 102 with the original and 96 to 98 with the variant with control vector, depending on the run; on the unchanged release it is the same, two tasks the model passes sometimes and sometimes not. Long prompts: the hidden number was found every time up to 250,000 tokens. Endurance: 90 minutes of mixed requests, 1,232 of them, none failed. Self-rescue: if the engine reports non-finite values and Strata's own retry does not help, the server restarts it once without the table and carries on in the slower, exact mode. The request that triggered it ends with an error, the following ones are answered; shown for both models with Strata's built-in fault injection.

The intermediate step: the same switches set by hand

Before my own build existed I set the switches by hand: a set of 28 that the unchanged engine knows, measured on 17 and 18 Nov 2026 on the 0.2.14 release: steel blue is Strata as shipped, amber the same engine with the switches in the run config. That was the intermediate step. Since then my own build carries 27 switches itself: of the 28, one became a fixed rule for the chunk size, one brought nothing and was dropped, one was added. Of the roughly 10 % in decode from that measurement little is left in my own build; it writes equally fast to slightly faster.

The price and the limits

The answers are not bit for bit the same as without the table, because the rounding changes; in my checks this does not show in quality. While reading, the card draws 25 to 30 W more (chapter 8). None of the switches is guaranteed by Strata: a release may rename or drop one, and the engine silently ignores an unknown name. I have not measured the RX 7900 XT, a card in a full PCIe x16 slot, another model or quant, or Windows.

When a new Strata release arrives

So there is a fixed procedure: first measure the unchanged release against the previous one, then apply the patch to the new source (it aborts if an anchor is missing), build, and run the chain above; only then do I switch over and re-measure the charts on this page. For 0.2.16 that meant: a new folder layout, a new build script, an adapted self-rescue test, and in the end the same figures as on 0.2.15. 06

Keeping the agent from making things up

A local model knows less than one from the cloud and does not like to admit it. The agent showed two weaknesses: it made up answers about things that do not exist, and it announced steps it has no tool for. I measured both first and then brought them down.

What belongs in the system prompt

RULES FOR THE SYSTEM PROMPT
Against making things up · my agent has run with this rule since 16 Nov 2026
Beantworte, was du weißt. Kennst du eine Sache, einen Namen oder ein Werkzeug gar nicht, sag das, statt etwas zu erfinden. Das gilt besonders für Befehle, Optionen und Ortsnamen: Kennst du sie nicht sicher, sag das, auch wenn sie plausibel klingen.
in English: Answer what you know. If you do not know a thing, a name or a tool at all, say so instead of making something up. This applies especially to commands, options and place names: if you are not sure you know them, say so, even if they sound plausible.
made-up things recognised: 104 of 120 · made-up command options: 17 of 24 · real questions right: 91 of 150, without a rule 95 (within the noise)

In addition, for agents with tools
Nenne nur Werkzeuge und Parameter, die du wirklich hast. Gibt es keins, sag: „Dafür habe ich kein Werkzeug.“
in English: Name only tools and parameters you really have. If there is none, say: "I have no tool for that."
wrong calls: 15 → 10 of 60 · justified calls: 41 → 32 of 50

Strict rule · instead, when a wrong answer costs more than a missing one
Wenn du etwas nicht sicher weißt, sage ausdrücklich „Weiß ich nicht“. Das ist eine richtige Antwort. Erfinde keine Fakten und keine Handlungen. Raten ist schlechter als Nichtwissen.
in English: If you are not sure of something, say explicitly "I don't know". That is a correct answer. Do not invent facts or actions. Guessing is worse than not knowing.
wrong answers: 58 → 30 of 150 · right ones: 90 → 84 · "I don't know": 36 times

The first sentence of the rule cuts the making up of things that sound foreign by about three quarters and costs no right answers. On command options and place names that sound plausible it fails on its own: the model recognised only 7 of 24 made-up options. The addition brings that back (17 of 24) without costing anything on ordinary questions. Rules with a fixed "I don't know" recognise a little more (21 of 24) but cost about every fifth right answer. How I arrived at these sentences is in the three measurements below.

Measure first: 16 questions per area, half of them made up

The probe asks about eight real and eight made-up things in each of five areas: towns, command options, theorems, books and parameters of the agent's own tools. Three rounds, five models, each without and with rules: 2,400 answers. I re-read the doubtful verdicts; an "I don't know" that still offers a guess counts as made up.

Four rules in the system prompt clearly reduce making things up on these questions

Without the rules the five models recognise only 17 to 60 % of the made-up things and invent the rest, most often the state of a made-up town and options that do not exist. With the rules it is 88 to 99 %. They still answer real things as correctly as before (117 to 120 of 120): the rules do not make them overcautious. A different model did not help; two dense models on the same card invented just as much and wrote at half the speed.

Counter-check with other questions: a short sentence helps, but not everywhere

The four rules name exactly the kinds of things my probe asks about. Hence the counter-check with public question sets I did not write: 150 things that do not exist, 150 hard and 150 medium real questions, 150 agent cases with a tool list, each with six versions of the system prompt.

The short sentence ("basic rule" in the chart) lowers the making up of non-existent things from 20 to 6 of 150 and leaves the answers to real questions as they are. The strict rule says "I don't know" four times as often for answers that were wrong without a rule as for right ones, but costs some of the right ones. The four rules of the first probe cost twice as many right answers and gain hardly anything. The tool sentence lowers wrong calls but also suppresses justified ones. The uncensored model behaves like the original on every point.

Follow-up: commands and places need a sentence of their own

The public question sets contain no command options. So my first probe ran again for the uncensored model, with three versions: the short sentence alone, the short sentence with the addition on commands, options and place names, and the four rules of the first probe. Of 24 made-up command options the model recognised 7, 17 and 21, of 24 made-up place names 12, 19 and 22, of all 120 made-up things 86, 104 and 113. On the 150 medium real questions 91 stayed right with the addition (95 without a rule, 76 with the four rules). One run each at temperature 0.7, every unrecognised answer read by hand.

For judgement, three rounds are not enough

The same three operating situations, asked ten times instead of three. A hard instruction ("if the number deviates, stop") is followed in 10 of 10 answers. Where the model has to weigh things itself, it looks worse than after three rounds: when a job aborts at night, it invents capabilities in 6 of 10 answers, such as "I'm pausing the collection". If you test an agent, ask every situation more often than is comfortable.

Hence three layers instead of one

The rules in the prompt catch made-up facts, but not announced steps. For those, the agent's tools now return a ready sentence and the allowed next steps, so the numbers come from code. And a small checker without a language model reads every answer: it flags unsupported numbers, announced steps without a tool and unknown tool names. In the agent answers it caught all six made-up abort answers, with no false alarm on the other tasks. It does not see made-up facts in plain words: of 269 made-up probe answers it would have flagged none.

Limits: the probe asks single questions without a conversation, with a short system prompt. How strongly the rules work inside a long agent prompt is not measured. The counter-check ran once per question and was judged by the same model; differences of a few answers mean nothing there. All measurements in detail · the checker plugin · the probe script

07

Uncensored: a model that refuses nothing

Chat and agent can use any model on this setup; it is chosen per conversation or in the agent's settings. One of them is uncensored. It is the same 125B model with its refusals removed: it answers whatever it is asked, including what the original model declines. There is no filter left, and it does not lecture. Technically a steering vector removes the direction along which the model refuses (abliteration); the weights stay the same.

Why: out of the box the model refuses or waters down a lot that is nobody's business on your own machine. An assistant at home should answer, not educate. Of 15 tasks that models often refuse, the uncensored one answers all, the original 11. Tasks, German and speed stay the same (measured on Strata 0.2.12; one or two tasks flip from run to run).

Does it make up more? Not measurably. Of 150 things that do not exist it treated 25 as real, the original 20; with a short rule in the system prompt it was 5 and 6. An agent needs the rules and the checker with either model.

What you take on: the model no longer distinguishes between a question that was refused wrongly and one the original declines for good reason. It answers both. The only line left is drawn by the person asking, and the responsibility lies with whoever runs it. It does not belong in front of children or in a service strangers can reach. Rebuild it in six steps

The basic setup needs only the NAS, the dock and the card, and runs entirely in the home network. If you only want the chat, stop after step 3.

  1. Set up the card

    UGOS Pro from 1.21 ships the firmware for the card. In the control panel under "Dedicated graphics card" leave the mode at "NAS". Switch the dock on first, then the NAS: OCuLink is only detected at boot.

    Pitfalls on UGOS

  2. Start the model server

    Strata loads the 125B model, llama-swap offers it under one address in the home network and unloads it after 30 minutes idle. Unloading is not about saving power, it is a protection: if the card drops off the bus with a model loaded, a kernel bug restarts the NAS.

    Launch configs

  3. Add the chat

    Open WebUI in a container, with one account per person. It talks to llama-swap's address, nothing else needs setting.

    Compose file

  4. Add web search

    SearXNG in the same stack. The chat searches the web through it, with no search account and no key. In my setup SearXNG queries the search engines through a VPN.

    Compose file

  5. Add the agent

    Hermes Agent with the local model: set the context to 256K, give the reasoning a token budget and put the rules against making things up from chapter 6 into the system prompt.

    Rules and checker

  6. Add OpenCode 2

    OpenCode 2 on your own computer, with llama-swap as a provider in the OpenAI format. Set the same model for session titles as for the work, otherwise the switch reloads for every title.

    Example config

The bottleneck is memory. With the 125B model loaded, 4.2 to 7.4 GiB of the 64 GB stay free, depending on the version; that is enough for chat, search and agent, but not for a second large service. If you need more room, pick a model that fits entirely on the card.
